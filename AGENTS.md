# Проект

- Сайт-портфолио Product Designer.
- Основной язык интерфейса и контента — русский.
- Дизайн предоставляется отдельно в Figma.
- Не придумывать и не менять визуальные решения без прямого запроса.
- Основной контекст работ: сложные B2B, B2E, SaaS и внутренние системы.

# Контекст и handoff

- Перед началом каждой задачи читать этот файл и короткий `HANDOFF.md`.
- Считать `HANDOFF.md` оперативным источником только актуального состояния, действующих решений, блокеров и следующего шага. Не превращать его в журнал всей разработки.
- `PROJECT_HISTORY.md` содержит архив завершённых этапов. Не читать его целиком по умолчанию; открывать только релевантные разделы при большой или рискованной задаче, возврате старого дефекта, архитектурном изменении или расследовании регрессии.
- `DESIGN_QA.md` содержит открытые визуальные дефекты. Читать относящуюся к задаче запись при исправлении конкретного экрана или формировании пакета pixel-perfect правок.
- При расхождении `HANDOFF.md` с кодом, Git или проверенным состоянием среды доверять фактическому состоянию и обновлять `HANDOFF.md`.
- Обновлять `HANDOFF.md` после завершённого этапа, изменения архитектуры/глобального решения, появления важного блокера, перед передачей работы или после deploy. Не записывать туда каждую локальную визуальную правку.
- Завершённую подробную историю переносить в `PROJECT_HISTORY.md` только когда она объясняет важное решение, проверку или причину системного дефекта. Не дублировать каждый commit.
- Не записывать в `HANDOFF.md`, документацию, Git или чат пароли, приватные ключи, токены и другие секреты.

# Классификация задач и режим исполнения

Перед составлением каждого нового исполнительного промпта:

1. определить размер: `SMALL`, `MEDIUM` или `LARGE`;
2. определить риск: `LOW`, `ELEVATED` или `HIGH`;
3. предложить режим `OPTIMIZED` или `FULL` и дать короткую причину;
4. определить границу Git-группы: какой законченный результат войдёт в commit и что явно не входит;
5. дождаться подтверждения пользователя; при несогласии обсудить классификацию;
6. только затем выдавать финальный промпт.

Размер оценивается по объёму и количеству затронутых экранов/компонентов. Риск оценивается отдельно по blast radius, переиспользованию, неизвестности причины, обратимости и влиянию на production.

`OPTIMIZED` использовать для понятных малых и средних задач с ограниченной областью влияния:

- собрать только непосредственный контекст, начиная с конкретного элемента и расширяя его лишь при обнаруженной зависимости;
- не писать отдельный план для очевидной локальной правки;
- если неверное значение или пропущенное свойство видно напрямую, считать это достаточной причиной и не устраивать глубокое расследование;
- выполнить минимальное изменение без смежного рефакторинга;
- обязательно один раз проверить изменённый результат на ближайшей достаточной границе;
- связанные состояния проверять только при изменении общего компонента, глобального стиля, общего источника данных или переиспользуемого поведения;
- не запускать полный аудит, не создавать избыточные QA-артефакты и не обновлять все документы без отдельной причины.

`FULL` использовать для больших, неопределённых или рискованных задач:

- явно зафиксировать scope, non-scope, этапы, критерии готовности, риски и stop-lines;
- загрузить расширенный релевантный контекст, включая нужные разделы `PROJECT_HISTORY.md`;
- при необходимости разделить реализацию на промежуточные проверяемые этапы с пользовательской приёмкой;
- проверить затронутые интеграции и связанные состояния;
- выполнить необходимые технические проверки и сохранить достаточные доказательства результата;
- обновить оперативный контекст и важную историю по завершении.

Production, VPS, DNS, SSL, firewall, секреты, доступы, миграции, данные и потенциально необратимые операции всегда относятся к `FULL`, даже если изменение состоит из одной строки.

Если исполнительный промпт уже содержит подтверждённые `size`, `risk`, `mode` и Git-группу, не классифицировать задачу повторно.

# Технологии

- Next.js с App Router.
- TypeScript.
- npm.
- MDX для контента проектов.
- Без Tailwind CSS.
- Без сторонних UI-библиотек, базы данных, CMS и авторизации без отдельного согласования.

# Правила разработки

- Изучать только непосредственную область задачи и расширять контекст при подтверждённой зависимости. Не читать весь проект ради локальной правки.
- Не менять файлы вне текущей задачи.
- Не проводить крупный рефакторинг без прямого запроса.
- Не добавлять зависимости без необходимости.
- Для новых зависимостей использовать конкретные стабильные версии.
- Сохранять строгую типизацию TypeScript.
- Не использовать any без необходимости.
- Не создавать декоративные заглушки и дизайн от себя.
- Учитывать адаптивность, доступность и производительность.

# Приоритет Figma и доступность

- Реализовывать утверждённый макет Figma без самостоятельных визуальных изменений.
- Любые Figma-файлы по умолчанию доступны Codex строго только для чтения. Запрещено создавать, изменять, перемещать, переименовывать или удалять в них узлы, компоненты, стили, variables, связи, свойства и любые другие данные.
- Запись в Figma допустима только при прямом явном требовании пользователя выполнить конкретное изменение. Даже при таком требовании перед любой записью Codex обязан отдельно описать точное действие и запросить подтверждение пользователя. Без полученного подтверждения выполнять запись запрещено.
- Разрешение на изменение кода, сайта, локальной документации или реализацию макета никогда не означает разрешения менять Figma. Публикация библиотеки и ранее выданный доступ к Figma также не являются разрешением на запись.
- Если требование WCAG можно выполнить без видимого отклонения от макета, выполнить его.
- При подтверждённом конфликте WCAG с Figma не останавливать работу и не спрашивать пользователя: реализовать вариант из Figma.
- Такой конфликт обязательно записать в `HANDOFF.md` и `ACCESSIBILITY_EXCEPTIONS.md`, а затем показать пользователю в итоговом отчёте.
- При наличии исключений не заявлять о полном соответствии WCAG.
- Для иконок обязательно соблюдать тип исходника Figma: `Line`/`Duotone` сохраняют настоящий SVG `stroke`, `Solid`/`Color` применяются только по подтверждённому mapping; использовать полный icon frame. Полный контракт — в `DESIGN_SYSTEM.md`.

# Проверки

- После любого изменения выполнить минимальную целевую проверку результата. Для визуальной правки это означает открыть конкретное место и убедиться, что изменение применилось в нужном состоянии.
- Не заменять минимальную проверку полным аудитом и не проверять несвязанные части сайта.
- Для текста, документации, ассета или очевидного локального CSS-свойства не запускать lint/build без дополнительной причины.
- Запускать `npm run lint`, когда менялась логика TypeScript/React, перед завершением логической Git-группы с кодом либо когда lint способен проверить конкретный риск.
- Запускать `npm run build` при изменении маршрутов, конфигурации, зависимостей, общей архитектуры, перед завершением большой Goal, PR, merge или deploy.
- Проверять связанные регрессии только если изменяется переиспользуемый компонент, глобальный CSS, шаблон, общий источник данных или навигационное/интерактивное поведение.
- Accessibility, performance, полный web-quality и полный Figma-аудит запускать по соответствующему риску или на крупном этапе, а не после каждой мелкой правки.
- Не повторять уже успешно пройденные проверки без причины.

# Git

- Не работать напрямую в main.
- Создавать ветку на логический workstream или крупную Goal, а не на каждую локальную правку. Связанные малые и средние задачи могут выполняться в одной действующей ветке после подтверждения пользователя.
- Перед большой/глобальной Goal по умолчанию создать чистую контрольную точку предыдущей логической группы: определить принадлежность незакоммиченных файлов, выполнить подходящую проверку, commit и при необходимости push.
- Один commit должен содержать один законченный и отдельно объяснимый результат. Не создавать commit на каждый пиксель, но и не смешивать разные экраны, подсистемы или уровни риска без причины.
- Границу Git-группы фиксировать до исполнительного промпта. Закрывать группу после достижения результата и подходящей проверки; начинать новую при смене экрана/подсистемы, цели, уровня риска или перед опасным изменением.
- Перед записью в код минимально проверить рабочую папку, активную ветку и наличие незакоммиченных изменений. Историю, remote и PR проверять перед новой Goal, commit/push, после долгой паузы, перед merge или deploy — не после каждого пикселя.
- Не выполнять merge без явного подтверждения пользователя.
- После завершения логической Git-группы самостоятельно создать commit. Push и создание/обновление Pull Request выполнять после завершения согласованного этапа либо когда это прямо указано в промпте; не делать отдельный PR для каждой микроправки.
- Перед пользовательской визуальной приёмкой запустить актуальную версию из текущих изменений; перед приёмкой этапа или deploy подтвердить production-сборку из точного HEAD, чтобы не показывать старый процесс или кеш.
- В кратком отчёте показать результат, актуальную ссылку, известные ограничения и что требуется проверить. Не создавать расширенный технический отчёт без необходимости.
- После разрешения:
  1. выполнить merge;
  2. переключиться на main;
  3. синхронизировать main с origin/main;
  4. показать git status и итоговый commit SHA.
